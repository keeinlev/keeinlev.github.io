Deep learning models are massive these days, and one of the most glaring tasks is understanding how and why they make certain decisions, from which have sprung the fields of Explainability and Interpretability.

We can get some intuition on what's going on inside these models through **attribution**, the process of assigning **importance** to the inputs and components of a model.

For example, if we had an image classifier receiving a picture of a cat as an input which correctly predicted the label "cat", we would expect a *faithful* attribution algorithm to assign positive importance to parts of the image such as the ears, eyes, and tail. If the model predicted "dog", we would expect to see which parts of the image made it think what it was seeing was a dog.
Another word for attributions is thus **heatmaps**.

Attribution algorithms can help us explain the model itself as well, assigning importance to the neurons or components based on their impact in the model's prediction. The idea of linking individual neurons in a model to certain human concepts has been famously propagated by Anthropic's Golden Gate Claude experiment, though they uncovered these findings using a different method called *dictionary learning* and a component called the *Sparse Auto-Encoder*. ([blog post](https://www.anthropic.com/research/mapping-mind-language-model) \| [paper](https://transformer-circuits.pub/2024/scaling-monosemanticity/index.html))

We, however, focus on the method called **Layerwise Relevance Propagation**.

# Layerwise Relevance Propagation (LRP)
LRP is an attribution method which is rooted in backpropagation, the process of sending signals backwards through a model's layers one at a time. At each layer, certain mathematical rules are applied to the signals based on the properties of the layer, taking into account both the contributions of each neuron and the structure of the component it lives in.

This allows researchers to progressively trace back what a model did for a certain example, layer by layer, based on the mathematical facts of the model. It does so until it reaches the input layer, thus explaining which pieces of the input contributed the most to the answer.

However, LRP had a problem with compatibility. Each new model architecture required its own tuned variant of LRP, one which would explicitly map the components to certain rules and establish the wiring between components for LRP to propagate through. Thus, the overhead of using LRP made using it non-trivial, despite multiple libraries such as Captum or Zennit existing which provided LRP capabilities.

# DynamicLRP
Our new implementation, DynamicLRP, serves to remove this barrier by using **dynamic computation graphs** (or just computation graph for short). A computation graph is essentially a blueprint and log of a model, specifying every operation that gets performed on a given model process, along with the connections through which the data flowed during that run. It's a powerful data structure which happens to also be the backbone of how we train neural networks, therefore the computation graph is typically always available to us for any model, and many deep learning frameworks have the capability to generate these graphs automatically, no matter the architecture used.

The key insight behind this is that computation graphs only look at the **atomic operations** of the model (Add, Multiply, Matrix Multiply, Sin, Log, etc.), instead of the big over-encompassing "modules" (Attention, Positional Encoder, etc.), which are logical groupings of operations or other sub-modules. By following this philosophy, we adapted LRP to work the same way, and to follow the computation graph as a map for how to perform the propagation.

# The Issue With Computation Graphs
Now, before continuing, it's important to understand the task we wish to accomplish. Starting from the output nodes of a computation graph (e.g. the green '(1)' node in the example above), we wish to propagate relevance values back up the graph until we reach the input nodes (in PyTorch, these are the `AccumulateGrad` nodes).

So, remember how I said computation graphs are the backbone of model training? Well, turns out that they are extremely specific to that task, which is to essentially compute derivatives. As a result, each node in the graph only stores the data required for computing the derivatives, or gradients (hence the keyword argument `requires_grad` involved in the tensor initializations above), at that node. The data stored is typically an intermediate result in the model's computation, called an **activation**. Sometimes, LRP will require activations that are not stored at the node in question (because they were not needed to compute the derivative of the operation), and so LRP would be unable to continue in a place where gradient propagation would be fine.

To resolve this, we created the **Promise System**. This modifies the propagation algorithm to *allow* these cases of missing activations, and actually continue past these bottleneck points to find the activations *further up in the graph*.
